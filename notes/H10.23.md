# H10.23 · 反馈④：定稿缩水真信号×4——起草余量＋推荐字数

新版脚本生效后的首次有效复验：4 节定稿缩水×4（非限流非超时），
3 节起草未足配额。用户另问 3 万字上限是否偏少、能否做推荐字数。

## 一、定稿缩水为何屡修不止

- 起草长度 ≈ 配额（Worker 字数闸在配额＋200 处中断）；
- 定稿是「修订」，天然删并重复，实测定稿/起草 ≈ 0.88–0.95；
  Worker runLoop 在 ≥0.9 配额且干净时即 done，前端按 0.9 起草
  验收恰在临界，擦线节三试皆「缩水」。提示词「不许缩水」治不住。

## 二、修复（纯前端，push 即上线）`scripts/book.js`

- planSections：每节新增 `share`（目标份额，Σ=T），`quota`
  改为 `round(share*1.12)`——起草预留收束余量；
- 起草验收与 shortfall 判定改用 share，口径与旧行为一致；
- 定稿验收改为「≥share*0.9 且 ≥起草*0.85」，截悬尾照旧；
- Worker 收到 inflated quota 后，0.9 配额早收 ≈ 1.008 目标，
  恰好落在目标上；不需 deploy。
- 蓝图陈示按 share，附注余量来历。

## 三、推荐字数（纯前端）

- 蓝图返回后按各章自报字数反推（章节占 86%：自序 8＋后记 6），
  百位取整、夹 4000–30000；与当前目标相差逾 5% 时浮出
  「采用建议字数 · N 字」按钮，一键重算份额；
- awaiting 阶段手动改字数同样重算（change 事件）。
- HTML：words-row 加 `#book-suggest`；版本号 bump 20261002b。

## 四、3 万字上限之答

当前架构的合理上限，非死限：逐节定稿每轮重发全书初稿
（PREV_TOTAL_MAX=30000），超限即截断；且节数越多耗时越长、
失败累积。放宽（如 5 万）须先做 payload 瘦身（只发本节初稿＋
最近 2 节定稿）并分段运行，留作后续。

## 五、验证

- node --check 通过；预期：复验全书 ≥0.95T，回退节数大降；
  若仍现缩水，下一步 Worker 侧改扩写式救援（续写易复述被剥）。
